# Shared-source bridge and durable caller intent

<!-- pdac-scope: cited -->

## Existing authority and query reuse

The workspace has process-local bounded owner sessions, separately connected GitHub user credentials, atomic source-request guards, bounded HTTP/asset reads and an offline Node result validator. Authentication currently uses ephemeral Data Protection. Keep those authentication/session semantics: the command journal does not persist provider or GitHub tokens and does not turn process restart into a longer login.

Add the SDK's observe/prepare/submit/reconcile operations to the existing workspace module. The shared observation supplies current questions, reservation coverage, capability and action decisions for #50/#51; labels and historical reports remain separate facts. Recommend an eligible pending-question response or eligible Propose/Refine only from the shared decision, never by recreating its admission rules. Unknown/incomplete source facts remain unknown. No framework or independent API service is needed.

## Request-scoped SDK bridge

Load the released public `@juangcarmona/lighthouse-sdlc/issue-control` export in one fixed Node helper. Inject transport, authority, bounded artifact reader and atomic caller claim explicitly; no ambient credentials, shell command or network execution is delegated to it. A bounded line protocol lets the .NET parent perform every HTTP request through the existing source guard: 4 MiB per frame, at most 64 callbacks, one outstanding callback per child, 20 seconds for the whole operation, a 128 MiB Node heap and two active children. Exceeding a bound returns unavailable/uncertain as appropriate; it cannot authorize a fallback. Source credentials stay in .NET memory and never enter child environment, arguments, stdin, logs or browser state. Keep child source calls serialized, correlate each reply to its outstanding request, reject malformed/extra frames, and kill/drain the exact child tree on timeout, disconnect or cancellation.

The parent binds the repository allowlist, immutable repository/issue/account identity and owner/connection generation. It permits only the SDK's supported account/repository reads and the exact prepared comment POST or router-dispatch POST, with the selected API version. A new source mutation needs a persisted claim and a fresh atomic owner/account/repository guard at HTTP initiation. No generic API proxy, arbitrary URL, PATCH/DELETE, label mutation, runner control, token fallback or approval endpoint is exposed. Signed artifact reads retain existing origin/initiation guards and ZIP/member limits; source provenance and policy validation remain in Lighthouse.

Authority intersects the verified acting user with the current matching App installation grants. The intended development matrix is Metadata read; Contents read for immutable workflow/contracts/proposals; Pull requests read for canonical proposal admission; Variables read for source policy; Actions read/write for artifacts and explicit dispatch; and Issues read/write for context and actual-user comments. The parent still allows only the exact prepared mutation, not every effect those App permissions could permit. No Contents write, variable write, installation-token impersonation, review approval or administration write is required. Runner-administration reads remain the separate #57 capability, never a prerequisite for issue controls.

Denied or unobservable installation/grant facts disable the dependent action. Missing development App permissions must be reported and consented through the owner-managed App configuration; entering a setting does not grant them. The separate Lighthouse CI App and production grants are unchanged.

## Proposed journal under ADR-0008

After maintainer acceptance, use one local SQLite database in an explicitly configured private directory. Use a separate persistent Data Protection purpose/key directory outside that database for sensitive intent/response payloads; leave authentication's ephemeral protector unchanged. Persist no source credential. Require trusted ownership/private permissions and no symlink redirection for journal/key paths; fail closed on unsafe, missing or unsupported persistence. Pin a framework-compatible Microsoft.Data.Sqlite version through the lockfile after checking the actual package.

Store immutable owner subject, actual source account, repository/issue IDs, action, SDK contract version, stable intent key, payload digest, source binding and creation time. Store transmission state and exact acknowledgment/run/comment/result evidence separately. A transaction and unique key claim precede the one possible source POST. Same key/payload returns the existing receipt; changed payload conflicts. While unresolved, equivalent submission is reused/blocked across clicks/tabs rather than assigned a fresh identity. A later intentionally new ordinary comment is distinct from reconnecting to a prior request. The original encrypted prepared intent remains the reconciliation input; browser-supplied serialized SDK effects are never trusted.

A crash after claim or a lost response stays uncertain and reconciles through the SDK's authenticated source identities/artifact indexes. Existing claims never cause another send. No background dispatcher, retry queue, label reset or newest-run correlation is added. A restored journal remains reconciliation-only for earlier claims. Unknown remote absence cannot be turned into permission to resend. If local disk/capacity/locking/protector failure prevents durable claim, no source write starts. Limit user comment bodies to 12 KiB within the existing 16 KiB request boundary. Use a 50 MiB logical SQLite database cap, 10,000 intent records, 64 KiB per protected intent/receipt and a two-second lock budget; report WAL/key storage separately rather than claiming that logical cap bounds total disk use. Persistence/acknowledgment failure retains the existing claim and never permits another send. A limit produces explicit unavailability rather than deletion of idempotency tombstones. No automatic retention policy is invented in this increment.

Journal reads require current owner, source actor and repository authority. Reconnecting the same authorized actor may recover its receipts; a new source actor cannot see old payloads, counts or questions. Logout stops new source calls and display updates; it neither cancels admitted repository execution nor discards the receipt of an already initiated effect.

## Browser behavior

Add an action area to the shared issue reader: acting identity, explicit effect, current eligibility/reason and source age. Server preparation returns an opaque journal intent ID and a plain-language summary; explicit submission references that ID with the existing CSRF/origin boundary. Recheck source facts before preparation and immediately before effect. Refresh/navigation/reload are reads, and reconnect reopens the existing receipt. Preserve input/focus where authorized; clear prior private scope atomically on known authority loss and ignore late old-generation responses.

Show local recorded/submitting/acknowledged/rejected/uncertain state separately from source admitted/queued/running/failed/completed and stage passed/blocked. A source acknowledgment or successful workflow alone cannot resolve a question. Only the SDK's validated matching continuation/result can establish consumed/resolved; newer or unavailable questions retain explicit context. An ordinary comment requires its own confirmation and warns when changing owner input can invalidate active publication. It never requests continuation. Unsupported approvals and source contexts explain their exact GitHub fallback.

## Validation and rollout

Use backend tests around the real SDK bridge with controlled provider responses and the real SQLite transaction/at-rest path. Cover direct unauthorized/CSRF requests, account/repository/generation change during source initiation, malformed protocol/oversized input, missing grants, competing claims, payload conflicts, crash-before/after-send, lost responses, restart/restore reconciliation, revoked sources and unavailable/expired artifacts. No test may accept a local lease or a fabricated source result as completion. Reuse the shared contract's policy tests rather than forking them.

Browser tests cover ordinary comment, explicit continuation, original-grant scope, disabled reasons, read-only reconnect, exactly correlated result, failed/unknown state, keyboard focus and 390px/light/dark layouts. Run full `npm run verify`, configured identity CI and independent review of all eleven Done dimensions: acceptance criteria, completeness, tests, quality checks, security, design conformance, documentation, product/spec consistency, evidence, review and known limitations. Capture actual connected App-user requests, denied/stale cases, duplicate/lost-response reconciliation and current-question resolution in development. No operator OAuth credential substitutes for that acceptance. The owner waived physical-phone rehearsal; do not claim it ran.

After acceptance, update owning arc42 building-block/runtime/security/recovery views through architecture-docs and the ADR workflow, documenting only implemented behavior. Before then ADR-0008 remains Proposed. Rollback disables the new controls while preserving journal/key files and source records for reconciliation; it must not re-enable sends for existing claims or interrupt repository execution. Production persistence, backups/key custody and deployment remain #58.
