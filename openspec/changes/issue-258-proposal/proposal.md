# Proposal

<!-- pdac-scope: cited -->

## Why

Issue [#258](https://github.com/juangcarmona/lighthouse-control-center/issues/258) needs source-backed evidence that existing Refine, ordinary comment, explicit Continue, Propose and recovery preserve the acting owner and exact request identity. Fixtures, HTTP success and completed workflows alone do not establish that journey.

## What Changes

- Define a bounded qualification record for the existing development preview selected by [owner answer 6944035493](https://github.com/juangcarmona/lighthouse-control-center/issues/258#issuecomment-6944035493). Reuse completed actions; do not repeat them for evidence.
- Correlate the initial question, non-continuing comment, explicit answer, resumed refinement and this fresh Propose request through their exact source receipts.
- Preserve failed proposal 44058084284/1 and the [owner-reported recovery](https://github.com/juangcarmona/lighthouse-control-center/issues/258#issuecomment-6944866940). Reconcile retained actions without preparing or sending again.
- Plan isolated negative checks, desktop/narrow visual evidence and a sanitized parent completion record, separating test execution from owner acceptance.

This is a candidate for owner review, assessed at `planned`, not an approved implementation. Keep `future`. No feature, dependency upgrade, schema/model edit, architecture change, implementation, integration, merge, deployment, privileged operation or issue closure is authorized.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

None. Existing requirements are unchanged. `.openspec.yaml` sets `skip_specs: true`; the scenarios in design.md qualify existing behavior rather than introduce a new specification.

## Impact

Only this proposal's planning artifacts change. Later evidence collection uses the existing authenticated controls, released SDK, protected journal and repository-owned workers. No new API, persistence field, source effect or migration is designed. Actual preview revision, bundled SDK version and connected-user prerequisites remain operational checks, not assumed deployment facts.

The baseline inventory contains `delivery-verification` and `github-user-connection`, read in full, plus `factory-overview`, `identity-environments`, `owner-access` and `visual-identity`; none needs a requirement delta. Active #48 controls/guidance, #51 intervention and #116 behavior-evidence plans overlap with this qualification but are not accepted anew or rewritten here. The draft structured-behaviour and access-continuity Product Changes remain separate.

## Product basis and impact boundary

Direct dependencies are FR-AUTHORIZED-ENTRY, FR-ISSUE-CONVERSATION, FR-INTERVENTION-INBOX, FR-EVIDENCE-CORRELATION, BR-EXPLICIT-WORK-COMMANDS, QR-EXECUTION-RECOVERY, QR-EXECUTION-SECURITY and QR-MOBILE-OPERATIONS. None is altered or contradicted. Current provider reports widen these to issue operation/intervention use cases, authorization/human-decision/source rules, execution and delivery-evidence terms. Those remain governing context; they are not new deliverables. Runtime administration, fleet health, scheduling, production custody and broader identity-provider qualification are excluded neighbours. No product drift is proposed.
