## Proposed initial measurement catalog for #54

These are candidate definitions for review, not measurements claimed available. Each stored result carries definition/version, purpose, unit, source adapter and record IDs, source revision, source/observation timestamps, window, expected/observed sample counts, applicability, freshness and limitations. Raw observations and derived calculations remain distinguishable.

| Measurement | Required producer and proposed calculation | Coverage / limitation |
| --- | --- | --- |
| Accepted mission throughput | Count distinct mission IDs with accepted-delivery receipts in a defined window | Issue closure, green worker and merged PR counts are separate; absent acceptance receipts are unavailable |
| Change lead time | Distribution from source commit time to confirmed successful production deployment of that change | Development-only repos are not applicable; repository-specific deployment semantics and missing comparisons explicit |
| Deployment frequency | Confirmed successful production deployments per elapsed window, with explicit environment and redeploy definition | Deployment object or GitHub release alone does not prove deployment; avoid inflating fan-out records |
| Change quality / rework | Explicit production/rework or PR correction receipts divided by the corresponding declared delivered-change sample | Keep planned bug work, implementation correction and production incident response separate |
| CI and verification | Outcomes/duration of identified check runs for exact candidate heads and attempts | Label eligible CI, independent verification and post-merge verification separately; all-jobs-skipped is not passed work |
| Coverage / mutation / security | Versioned repository CI facets, with tool/scope/commit and sample age | Missing producer or expired artifact unavailable; no test count-to-coverage inference |
| Autonomy / intervention | Accepted eligible missions delivered within their grant without human correction, plus separately counted protected decisions and intervention reasons | Define cohort, denominator and missing mission histories; required approvals do not automatically indicate failure |
| Tokens / duration / retry | Lighthouse usage events deduplicated by producer event IDs and native/fallback precedence, correlated to exact attempt | Partial fields, compaction exclusions, clock gaps and missing stages remain explicit |
| CPU / memory / GPU / storage | Provider probes and execution cgroup counters with sampling interval and units | Runner busy is not CPU usage; cumulative counters need deltas; unsupported GPU/namespace counters null |
| Attributable cost | Reported inference/provider charges joined by provider request/session IDs; any estimated rate is separately labeled/versioned | Tokens, configured model and zero engine cost fields do not attest billing; partial attribution cannot become total mission cost |

Start with one reproducible supported operational signal and its unavailable cases. Add production and cost measures only when the relevant producers and retention exist. OpenTelemetry provides transport and correlation; a collector/dashboard stack is optional, and adds no source authority.
