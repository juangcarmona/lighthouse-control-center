# Repository configuration inspection

On a configured repository page, choose **Inspect configuration** to read its configured branch. Lighthouse Control Center resolves the branch once, then binds every file read to that exact commit. The connected GitHub user and the configured GitHub App installation must both have current access to the repository; the App needs `contents: read`. The read-only endpoint is `GET /api/repositories/{owner}/{repository}/configuration`. It does not accept paths or refs from the client, and other HTTP methods are not mapped.

The reader checks `lighthouse.json`, `.lighthouse/upgrade.json`, `.lighthouse/sdlc.json`, `.lighthouse/commands.json`, root `package.json`, and a supported npm version-3 `package-lock.json`. A valid manifest can name at most two `.github/workflows/*.yml` sources for bounded inspection. Other managed paths are left unknown and make coverage partial. The reader does not follow paths outside that allowlist, execute YAML, contact a package registry, start workflows, change files, or create issues.

Each source and fact includes its path, immutable commit and observation time. Manifest pins, npm declarations, lock resolutions, capability and projection versions, adoption records, profiles and contract identities remain separate facts. Multiple declarations and lockfile locations remain visible. Unsupported or unknown schema combinations expose a diagnostic and a link to the exact source file; their fields are not treated as validated facts. Workflow content is represented by a SHA-256 digest because workflow syntax and embedded tool versions are outside the supported interpretation.

Supported npm identities include `@prodshape/cli` and `@arcshape/cli` as well as the legacy `@juangcarmona/productshape` and `@juangcarmona/arcshape` names. These remain separate packages, not aliases: a manifest integration pin does not establish the version of a differently named npm package.

The comparison controls inspect a second configured repository only after the operator explicitly selects it. At most two repository projections and 4 MiB are retained in browser memory; this state is never written to browser storage. The operator then selects an observed fact as a comparison baseline. Exact three-part numeric package versions are ordered with integer arithmetic only when component, fact kind and contract identity agree. Equal opaque values are identified as equal source values; incompatible facts and ranges have no inferred ordering. A comparison describes observed values; it does not establish compatibility, a required upgrade or a policy violation. Latest available, installed and required-by-policy values remain unknown. No released exception-validity contract is supported, so a source declaration cannot establish validity or suppress a difference.

Inspection is bounded to one branch lookup, at most eight content reads, two managed workflow reads, 256 KiB per decoded file, 1 MiB of decoded content in total, a 30-second deadline and a 2 MiB response. An aggregate or per-file limit leaves the remaining sources unknown; content is never truncated into a valid fact. Missing, denied or unsupported files do not prove a package or configuration was never adopted. The server coalesces matching reads for 15 seconds only after checking current authority. Older retained browser evidence is labelled stale; the user refreshes explicitly. Account, session, repository or permission changes clear affected projections and comparisons.

For `.lighthouse/upgrade.json`, a `nextAction` value becomes a maintenance link only when it is exactly `#<issue-number>` in the same repository or an exact GitHub issue URL for another configured repository. Arbitrary text and unsafe or unconfigured URLs remain plain text. The link opens GitHub directly; the inspection does not search for work or assert that an issue is missing.

The bundled Lighthouse CLI 0.12.65 manifest and upgrade schemas and npm tarball digest are recorded under [`openspec/changes/issue-53-proposal/evidence/schemas/lighthouse-0.12.65/`](../openspec/changes/issue-53-proposal/evidence/schemas/lighthouse-0.12.65/). This is provenance for the released schema, not a claim that the current repository's 0.12.68 manifest was validated against a 0.12.68 schema. The SDLC 0.22.4 contract/schema source receipt and static closed-schema incompatibility check are recorded under [`openspec/changes/issue-53-proposal/evidence/schemas/sdlc-0.22.4/`](../openspec/changes/issue-53-proposal/evidence/schemas/sdlc-0.22.4/). SDLC and command declarations remain raw, unsupported evidence.

## Browser verification evidence

The PR #197 correction retains a supplemental `configuration-browser.mjs` script in its workflow evidence, without changing frozen browser-test inputs. With dependencies installed, run the retained script through the managed command slot from the disposable workspace: `node /harness/src/managed-command.mjs run /output/evidence/commands configuration-browser-replay -- node /output/evidence/configuration-browser.mjs configuration-browser-replay`. It starts and stops the existing static fixture server in the same command and explicitly uses `/usr/bin/chromium`.

The successful `browser-04` receipt and `configuration-browser-04/report.json` identify the supplied source revision, candidate diff, fixture origin, viewport, theme, assertions and GET-only request traces. The report accompanies 32 screenshots covering matching, exception-unassessed, outdated, stale, conflicting, root npm not-applicable, inaccessible and unsupported states at 1280px and 390px in both themes. It also checks keyboard activation, retained/removed source focus, unrelated-control focus, horizontal overflow and Axe accessibility. Failed earlier attempts remain separate artifacts, not passing evidence. These are synthetic source-response fixtures derived from committed package declarations, not live GitHub observations or physical-device acceptance. Required host verification, exact-head CI and independent review remain separate.
